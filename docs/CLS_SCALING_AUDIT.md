# Разбор CLS-экспериментов из 1a0f4f2

Проверены `figures/cls_scaling_check/{rms,none_matched,none}`: одно лицо
`glasses_180_1`, seed 500180, alpha 0.5, все 19 double-блоков, 20 Adam-обновлений
на каждом из четырёх шагов. Коммит добавил результаты; код прогона соответствует
предшествующему `eef61c6`. Версии в provenance: torch 2.6.0+cu118, diffusers 0.38.0,
transformers 4.49.0. SHA направления совпадает во всех трёх режимах.

## Что видно в результатах

Все baseline и alpha=0 совпадают попиксельно. RMS и matched-вариант портят лицо,
волосы и фон; очки остаются. Без RMS искажения меньше, но лицо и фон меняются,
очки также остаются. В коммите сохранены one-step картинки до/после только шага 0;
логи содержат все четыре шага.

| Режим | Loss на шаге 0: до → первое обновление → двадцатое | RMS изменения velocity после первого обновления | MAE финального RGB от baseline, шкала 0–255 |
| --- | --- | --- | --- |
| rms | 0.026520 → 0.275028 → 0.021557 | 0.7849 | 73.0024 |
| none_matched | 0.026520 → 0.273810 → 0.021660 | 0.7902 | 66.9505 |
| none | 0.026520 → 0.092721 → 0.014809 | 0.6112 | 38.6015 |

В RMS-режиме на sigma=0.75 **все 20 обновлений** дают loss хуже начального. Режим
`selection: "last"` всё равно применяет последнее обновление: это заданная
конфигурацией политика, а не потерянный результат оптимизации. RMS-потолок и штраф
на активации отключены. Градиенты всех блоков ненулевые.

Это показывает агрессивное первое вмешательство и несовпадение снижения CLS-loss
с удалением очков. Само повышение loss не доказывает ошибку знака градиента:
слишком большой шаг тоже может перескочить область убывания.

## Воспроизведённые ошибки в пути изображения

В прежнем one-step objective `x0` вычислялся в FP32, затем в FP32 выполнялись VAE
scale/shift, и только после этого делался BF16-cast. Реальный scheduler возвращает
sample в dtype velocity **до** VAE scale/shift. Кроме того, RGB objective вычислялся
в FP32 без clipping, а выход пайплайна проходит штатное приведение RGB в [0,1].

Порядок операций scheduler сверен с исходником
[diffusers v0.38.0](https://github.com/huggingface/diffusers/blob/v0.38.0/src/diffusers/schedulers/scheduling_flow_match_euler_discrete.py#L444).
В `tests/test_cls_rendering.py` эти несоответствия воспроизводятся на маленьких
случайных CPU-моделях, без pretrained-весов: до исправления 6 из 8 сочетаний
FP32/BF16, насыщенного/обычного RGB и 3/4 шагов нарушали контракт последнего шага.

Исправление объединяет декодирование в `src/dino_adapter/cls_images.py`.
По умолчанию используется `decode_mode: "pipeline"`; режим
`legacy_fp32_unclipped` сохраняет старое поведение для воспроизведения.
Проверка требует точного совпадения последней one-step RGB-картинки, возвращаемого
float RGB и CLS, включая насыщенные пиксели. Округление до 8-битного PNG остаётся
отдельной операцией; в результатах записывается `evaluated_to_png_cls_l2`.

Нельзя заключить по имеющимся PNG, что именно эти ошибки объясняют весь ущерб лицу.
В старых логах нет диапазона RGB до clipping и его CLS после clipping. Новые логи
сохраняют `decoded_out_of_range_fraction`, `dino_rgb_min`, `dino_rgb_max`.
Исправление не вводит RMS-бюджет, штраф сохранения или откат обновлений.

## Нерешённая проверка градиента на CUDA

У RMS и matched-контроля при нулевой поправке совпадают исходные изображения и
loss. Однако нормы первых градиентов после пересчёта координат отличаются примерно
на 0.5–1.0% по блокам. Даже `none` и `none_matched` имеют разные начальные нормы
градиентов, хотя LR ещё не использовался. По этим агрегатам нельзя определить,
является ли причиной недетерминированный CUDA-backward, BF16 или другой фактор.

Финальные RGB у RMS и matched-контроля отличаются друг от друга на MAE 41.4173/255.
Маленькие CPU-тесты эквивалентности не гарантировали такого же поведения на полных
CUDA/BF16 моделях. Для проверки нужен повторный backward в одном и том же состоянии
и фактическая зависимость loss от знака/размера пробного шага.

## Короткий диагностический запуск на кластере

Из корня SHIFT, с активным окружением:

```bash
python -m src.dino_adapter.cls_experiment \
  --config configs/cls_joint_debug_first_update.json \
  optimize --dataset out/dataset200 --split test --num-samples 1 \
  --direction out/cls_features/cls_direction.pt \
  --output out/cls_first_update_debug
```

Укажи фактический путь к направлению и новый каталог результатов. Это диагностика
первого обновления: все double-блоки, шаг 0, один Adam update. Остальные три шага
генерации проходят без вмешательства. Это не новая рекомендуемая схема редактирования.

До обновления проверяются множители направления Adam
`[-0.1, -0.01, -0.001, 0, 0.001, 0.01, 0.1, 1]`. При нуле повторяется backward.
После диагностики восстанавливаются нулевые поправки и выполняется исходный Adam
update. Пробы не меняют LR, optimizer state и политику принятия обновлений.

В JSON найди записи `phase: "first_update_probe"`:

- `repeat_gradients`: cosine и относительное L2-различие повторных градиентов
  каждого блока. Сначала оцени их воспроизводимость.
- `predicted_linear_loss_delta`: предсказание первого порядка по исходному градиенту.
- `observed_loss_delta`: реально измеренное изменение loss при пробном множителе.
- `velocity_relative_rms`: насколько проба меняет выход трансформера.

`provenance.json` дополнительно записывает SHA исходных файлов, режим decode,
CUDA-версию PyTorch и флаги детерминизма/cuDNN. Это позволяет отличать изменения
кода и окружения при повторных запусках.

Положительный множитель идёт по направлению Adam; отрицательный — против него.
Если малые положительные шаги снижают loss, а полный шаг повышает, это свидетельство
перелёта. Если повторные градиенты устойчивы, но направление не подтверждается
пробами, проверяй градиент и влияние dtype; BF16-квантование может давать плато для
очень маленьких шагов. Одно плато не доказывает неверный градиент.

## Направление и оставшиеся ограничения проверки

Знак в коде согласован: `d=mean(CLS_с_очками)-mean(CLS_без_очков)`, цель
`normalize(CLS_source-alpha*d)`, Adam минимизирует расстояние до неё. В dataset
используются train-пары для направления и held-out пары для прогона. Однако сами
кешированные CLS и обучающие картинки в новом коммите не представлены; их
семантическое качество по этим артефактам проверить нельзя.

Проверка направления по существующему кешу без GPU:

```bash
python -m src.dino_adapter.cls_experiment audit \
  --features out/cls_features/cls_features.pt \
  --direction out/cls_features/cls_direction.pt \
  --output out/cls_direction_audit.json
```

Разделимость train/val/test не доказывает, что движение вдоль направления удаляет
очки. В текущем loss нет независимого критерия сохранения личности; DINO CLS сам
по себе не гарантирует сохранение лица. Ранние one-step оценки также отличаются
от финальной картинки после оставшейся диффузии. Эти ограничения нельзя устранить
одной проверкой hooks или прохождением CPU-тестов.

## Локальная проверка исправления

Полный набор: **130 тестов прошли** на CPU, без загрузки pretrained-весов.
В том числе проверены градиенты относительно явного forward для всех 19
double-блоков на маленькой случайной модели, FP32/BF16, checkpointing,
совпадение последнего objective с выходом пайплайна, неизменность Adam-обновления
при включении диагностических проб и удаление hooks при исключении.
Локальные версии: torch 2.14.0, diffusers 0.40.0, transformers 5.17.0.
Это проверка реализации; результат на FLUX с кластера ещё не получен.
